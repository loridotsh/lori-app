# Lori product guide

Understand what Lori does, why each feature exists, who it helps, and how to use it.

## Choose a guide

| Guide | What it explains |
| --- | --- |
| [Lori application](LORI_APPLICATION.md) | Code and Work: workspaces, agents, conversations, files, Git, extensions, providers, automations, documents, visuals, memory, and settings. |
| [Lori Enterprise](LORI_ENTERPRISE.md) | Company setup, people, teams, devices, access, managed AI, Cloud Work, shared projects, reporting, and administration. |

**Lori** is the application people work in. **Lori Enterprise** is the company's platform for managing access and providing company Cloud Work. The application guide explains the individual experience; the Enterprise guide explains how company and shared work fit around it.

Each feature has a plain description and a **Why use it** explanation. Features are grouped by the job a person is doing. Short examples show how the features work together. Availability and source references are kept at the end of each guide.

For installation, development commands, and code structure, use the existing [Lori README][desktop-readme] and [Enterprise README][enterprise-readme].

## Documentation approach

These guides were rebuilt from the current interface composition, settings, tool catalogs, and relevant native/API behavior, reviewed on **22 October 2026**. They describe existing functionality, with capability and policy limits where relevant. They are product explanations rather than a new runtime or release certification.

The writing approach follows [Google's audience guidance][audience]: explain the knowledge a new reader needs and define unfamiliar terms. It uses [Diataxis explanation guidance][explanation] to connect what a feature does with why it exists, and [Microsoft's instruction guidance][instructions] for short, located user workflows. Developer setup stays in repository documentation so a product reader can follow the guide without learning the implementation first.
